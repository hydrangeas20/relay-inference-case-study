# RLY-4: "We turned on prefix caching. Nothing changed."

## Customer complaint

> "We enabled prefix caching like the docs said. Nothing changed."

## Root cause (planted)

Relay's prompt template puts a timestamp and request ID at the **top** of the system prompt. Every prompt starts differently, so the cache almost never hits.

## Reproduce

1. Send completions traffic using Relay's prompt template with prefix caching enabled.
2. Show the near-zero cache hit rate from server metrics.

## Fix

- Reorder the template: stable content first (system prompt, repo context), variable content last.
- Re-run the same traffic.

## Acceptance criteria

- [ ] Cache hit rate before and after, from server metrics.
- [ ] TTFT distribution (p50/p95/p99) before and after, same traffic trace.
- [ ] The diagnosis explains *why* the hit rate was near zero, not just that it was.

## Proof

TTFT distribution before/after, and cache hit rate over the run.

## Connects to

The largest single TTFT win, which relieves pressure on RLY-1.

## Findings

**Source: `cpu`.** llama.cpp `llama-server` (commit `2280f0f`) on one CPU thread, with a Qwen2-architecture model that has seeded random weights and the real Qwen2 tokenizer ([ADR-0007](../../docs/decisions/0007-cpu-engine-and-rly4-method.md)). That makes these real engine and cache measurements. They are not GPU or vLLM latency, and the synthetic weights mean they say nothing about completion quality.

Predictions and falsification thresholds were committed before any full run was read: [PREDICTIONS.md](PREDICTIONS.md). All numbers below are generated by [`analyze.py`](analyze.py) from [`results/rly-4/`](../../results/rly-4/) ([report.md](../../results/rly-4/report.md), [report.json](../../results/rly-4/report.json)).

### Diagnosis

Relay's template starts every prompt with `[relay request_id=… ts=…]`. A prefix cache can only reuse a run of tokens that matches from the **first** token, so two prompts share only the tokens before their first difference, whatever follows.

With the original template, llama.cpp served **0.5%** of prompt tokens from its cache. That's the shared opening of the header text: 0, 7 or 10 tokens a request. Turning caching on did nothing useful: TTFT with the cache on was no better than the cache-off control (see the predictions table for the exact comparison).

The header is 60 characters, 43 tokens, of a prompt with a median of 1,780 tokens (2.4%). It isn't expensive to process. It's expensive because of **where** it sits: at the front, it makes every token after it impossible to reuse.

### Experiment design

| | |
| --- | --- |
| Question | Is the per-request header the reason prefix caching did nothing, and how much TTFT does removing it recover? |
| Workload | 8 editing sessions × 6 completion requests = 48 requests per run. Each session sends one real source file (pinned corpus) from its start to a cursor that begins at 6,000 characters and advances 80–240 characters per request. Prompts are 1,470–2,400 tokens (median 1,780) |

| Server | Fresh `llama-server` per run (cold cache), 1 slot, 1 thread, pinned to CPU 0; gateway and load generator pinned to CPU 1 |
| One change at a time | Template (`original` vs `metadata`), and the server's prompt cache (`--cache-prompt` vs `--no-cache-prompt`) |
| Negative control | The same arrival times and cursors, but every request uses a different file, so no file context repeats |
| Repetitions | 3 per configuration were planned (15 runs). 4 failed the send-lag self-check and are excluded. 2 extra cache-off runs were added **after** the analysis showed that control with 1 valid run and P5 failing: they are post hoc (see predictions below). 17 runs in total, 13 valid |
| Evidence of mechanism | Per-request `cache_n` and `prompt_n` reported by the server in each response, cross-checked against its Prometheus counters |

### What changed

- **New template variant** (`src/relay/gateway/templates.py`): `PROMPT_TEMPLATE=metadata` drops the header from the prompt.
- **Request ID moves to metadata:** the gateway sends it upstream as `X-Request-Id`, so tracing survives without touching the prompt.
- **Baseline kept:** `original` stays the default, byte for byte.
- **Why not move the header to the end:** an inline-completion prompt ends at the cursor, so trailing text would sit between the code and the completion ([ADR-0007](../../docs/decisions/0007-cpu-engine-and-rly4-method.md)).
- **Regression tests** (`tests/test_rly4.py`) pin the property the fix depends on: with `metadata`, every later prompt in a session starts with the entire earlier prompt. With `original`, two prompts diverge within the header.

### Uncertainty

The headline is reported with its run-to-run spread, not a confidence interval. The paired median ratio was 0.210, 0.223 and 0.220 in the three repetitions (run *k* of each arm paired with run *k* of the other).

A bootstrap that resamples both runs (within each arm) and whole sessions gives 0.18–0.24 for the paired median. That's a rough bound, not an exact interval, for two reasons:
- **Few runs.** With 3 runs per arm, the run level has only a handful of distinct resamples.
- **Linked sessions.** Sessions ran back to back on one server, so queueing links neighbouring sessions.

The figures are in [review/recompute-output.txt](review/recompute-output.txt).

**Not predicted:** with the original template, turning the cache **on** was about 9% slower than the cache-off control, and only 12% of requests were faster. The header's 43 extra tokens (2.4% of the prompt) explain part of it. The rest shows up as a 6% higher prefill cost per token in that condition (1.149 vs 1.080 ms/token, server-reported). The cause wasn't tested: cache bookkeeping, attention cost over longer prompts and between-run noise all remain possible. Either way, the customer's report holds: turning caching on didn't help.

### Why it works, and the trade-offs

- **Follow-up requests reuse almost everything.** With the fix, each request after the first in a session matches the previous prompt up to the old cursor. The engine evaluated a median of 40 tokens per follow-up (22–135). Some follow-ups re-evaluated more than the newly typed text alone would need; that wasn't investigated. Follow-ups had a median TTFT ratio of **0.21**: about 5x faster.
- **The first request in each session gains too, but less** (median ratio 0.71). It still prefills the whole file. It gains because the server is less busy, so it waits less in the queue.
- **The same hardware does less work.** The server was busy 52% of the time on the original template and 21.5% on the fix, for the same 48 requests. That freed capacity is what would let a GPU fleet serve more users per replica. Sizing it on a GPU is a separate, `gpu`-tagged measurement.
- **Trade-off 1: request metadata leaves the prompt.** Anything that relied on reading the request ID from the model's input or logs has to read the `X-Request-Id` header instead.
- **Trade-off 2: the cache only pays when context repeats.** In the negative control (no repeated file context), the fix reused only the system prompt: cache share went from 0.5% to 4.0%, and median TTFT ratio was 0.90.
- **Trade-off 3: cache memory.** Reuse depends on the server keeping a session's KV state until its next request. With many concurrent users, eviction will lower hit rates. This experiment doesn't measure that.

### Limits of this result

- **CPU, not GPU.** One CPU thread prefilled about 870–930 tokens/s here; a GPU runs Relay's 7B model far faster. The milliseconds don't transfer. The cache share doesn't necessarily transfer either: vLLM caches whole fixed-size blocks, evicts under memory pressure, and the real model has its own tokenizer. It has to be re-measured on vLLM before it goes into capacity planning.
- **Synthetic weights.** The model's outputs are meaningless, so nothing here bears on completion quality. Prefill cost depends on architecture and token count, which are real.
- **One user's session at a time, one server slot.** The workload doesn't interleave sessions from many users, and doesn't exercise eviction or routing across replicas.
- **Small samples.** There are 48 requests per run, so p99 is roughly the slowest request. p99 is reported but not used for any conclusion.
- **Not every run was valid.** Runs that failed the load generator's send-lag check are excluded and listed in [report.md](../../results/rly-4/report.md). The p50 and p95 differences are much larger than the spread across valid runs.
- **Sessions are modelled.** The editing-session shape (6 requests per file, 80–240 characters typed between requests) is an ASSUMED workload, not fitted to Relay data. The size of the win scales with the share of requests that are follow-ups.

### Recommendation to Relay

1. **Ship the template fix.** Take per-request metadata out of the prompt and carry it in request headers. It's a one-line template change with no model change, and it's what makes prefix caching do anything at all.
2. **Watch the server's own cache counters.** On vLLM that's `vllm:prefix_cache_hits` / `vllm:prefix_cache_queries`; on llama.cpp, `llamacpp:prompt_tokens_cached_total`. Alert if the hit share drops toward zero. A share near zero on a workload that should repeat context means something in the prompt changed again.
3. **Add a template regression test to Relay's CI.** It should check that two requests for the same context share their whole prompt prefix, like `tests/test_rly4.py`. Any future edit that puts per-request data near the top of the prompt then fails before it ships.
4. **Before counting the capacity gain, measure it on Relay's GPU setup with vLLM** using these traces. Then test many interleaved sessions to see how eviction and replica routing affect the hit share.

### What I'd do with more time

- Re-run on vLLM with a GPU (`gpu` source), using the same traces and the same switch.
- Interleave many users' sessions on a multi-slot server to measure the hit share under eviction. Then decide whether replicas need prefix-aware routing.
- Measure a sliding prefix window. Editors that send only the last N characters before the cursor change the prompt's start on every keystroke, which defeats prefix caching the same way the header does.
